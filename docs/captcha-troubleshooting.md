## 已坐实的代码问题

1. **超时被写成了答案拒绝。** `nine.solve()` 仅在等待成功/错误回调 12 秒超时后打印“答案被拒绝”。这不是服务端明确判错的证据。没有现场图，不能根据相似度数字确定是漏选、误选、点击未生效，还是验证状态没有回传。
2. **关闭状态不在求解器等待条件内。** 页面原先把关闭事件写成 `closed`，但 Python 仅等待 `success` 或 `error`。关闭会等到超时；成功之后若触发关闭，还有覆盖未读取成功结果的风险。这是可复现的代码缺陷，但历史日志不足以证明当时触发过关闭事件。
3. **刷新只检查元素存在。** `open_panel()` 采用固定休眠，随后只检查图片元素是否存在，没有确认刷新完成、图片加载完成、面板可见或图片内容已更新。这个缺口与后续取图异常相容，但不能只据日志断言它就是历史故障的唯一原因。
4. **取图错误缺少响应信息。** `fetch_image()` 读取字节后直接交给 Pillow，未记录 HTTP 状态、Content-Type、响应长度和解码后尺寸；重试还会在原 URL 追加参数。旧异常只能证明响应无法解码，不能证明它必然是 HTML、风控页、空响应或某种特定图片格式。
5. **故障现场会被后续求解覆盖。** 外层每次调用 `_solve_local()` 都清理同一个目录；两处旧测试在 mock 求解器时，仍会走真实目录清理。已在独立临时目录内复现删除旧现场的行为。排查时真实现场目录为空，但无法认定历史文件具体是被哪一次运行清掉的。

## 本轮已实施的修复

- `core/captcha.py` 为每次求解创建独立的 `captcha_debug/session-<UTC时间>-<随机编号>/`，外层重试和并发请求不会共用图片文件。
- 每轮日志输出现场编号，`summary.json` 保存开始/结束时间、本地求解状态、回调超时/图片获取失败/其他异常等分类计数及异常类型。不保存账号、gt、challenge、validate、URL 或原始异常消息。
- `summary.json` 的 `success` 只表示本地求解器取得验证结果，**不表示后续米游社校验或签到已经成功**；最终业务结果仍须查看任务日志。
- 正常情况下只保留最近 20 个、且未超过 7 天的已完成现场，在下一次求解结束时清理。只删除本模块可识别的图片、分数 JSON 和摘要；不递归删除，不跟随链接或 Windows junction，不清理运行中的目录、旧版根目录文件、用户笔记或未知内容。崩溃遗留的 `running` 目录保留供人工排查，不保证自动清理这类现场。
- 现场目录不可写、摘要损坏或写入失败不会丢弃求解成功结果。
- 在现有调用边界把误导文案改为“12 秒内未收到成功或错误回调”，不改变 `nine.py` 的识别、等待和重试行为。
- `harness.html` 将关闭事件转换成现有等待条件可读取的错误状态，并保留成功后自动关闭时的验证结果；成功回调拿不到验证结果时返回明确错误，组件报错时清除旧结果。
- 两处旧测试均改用独立临时目录，新增假页面、假图片、并发目录、历史留存及页面回调回归测试。

## 后续取图与刷新修复方案（尚未实施）

按此前“保留 `core/geetest/nine.py` 不改”的约束，本轮没有修改该文件，也没有复制识别器或用运行时替换绕过约束。因此，**历史图片解码故障尚未被证明消除**。

后续若调整该文件，建议按以下顺序实施：

1. 先补取图诊断：HTTP 状态、Content-Type、字节长度、内容摘要哈希、解码格式及尺寸；日志不输出完整 URL、查询参数或响应正文。区分传输失败、响应不可解码、图片尺寸不符。先取得证据，不凭异常字符串猜来源。
2. 刷新改为有截止时间的状态等待：面板可见、九格及确认按钮有有效坐标、图片加载完成且尺寸合理，并通过可观测的刷新过程确认拿到有效图片。不能只凭元素仍在 DOM 中认定刷新成功，也不应只凭 URL 必须变化来判断内容是否更新。
3. 图片不可解码或面板无效时，不对旧格子继续点击；将这一轮标记为取图/面板错误，按既有有限预算退出或重新申请验证码。不要单纯把 3×5 层重试再加大。
4. 提交后的诊断区分成功、组件错误、窗口关闭和超时；超时保留有限的页面状态及耗时记录，不能再统一归为答案错误。只接入当前 SDK 确实提供的事件，不混用其他版本的回调契约。
5. 在有匿名化现场图片、人工核对和基线对比之前，保留现有相似度阈值、裁图及最多选格规则。识别准确率问题应独立验证，不能用盲调阈值代替取图与状态修复。
